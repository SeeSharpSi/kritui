# Purpose

- Build the LLM chat UI as server-rendered hypermedia. Return templ-rendered HTML fragments for interactions; do not turn it into a client-rendered JSON application.
- Browser-side dependencies are limited to htmx, a-h/templ, and basic CSS. Do not add a JavaScript or CSS framework. Prefer readable modern CSS, including nesting where useful.

# Workflow

- Go is pinned to 1.25.3 in `go.mod`.
- A fresh checkout has no generated template Go files. Run `go run github.com/a-h/templ/cmd/templ@v0.3.1020 generate` before building, and after every `templ/*.templ` change. `templ/*_templ.go` is ignored; never edit it manually.
- Run the app with `go run .`; it listens on fixed address `:8080`.
- Only edit files specified by the user. If you need to edit other files, ask before doing so.
- Full verification: `go test ./...` then `go vet ./...`. Current tests use local `httptest` servers and need no external services.
- `Dockerfile` generates templates, runs full tests and vet, then builds the binary. Keep every imported package directory in its explicit `COPY` list. Build and runtime stages both require Git because Git-tool tests and production Git tools execute its CLI.
- `.forgejo/workflows/container.yml` publishes commit-SHA and `main` tags to the Forgejo registry after successful `main` builds. Registry credentials remain organization Actions settings, never repository files.
- Focus a package with `go test ./llm`, `go test ./tools`, or `go test ./tools/git`; focus one test with, for example, `go test ./llm -run '^TestComplete$'`.
- After large changes, update the AGENTS.md file accordingly. Keep it concise.

# Architecture

- `server.go` is the HTTP entrypoint: `GET /` renders the page, `GET /healthz` checks local database readiness, history and chat mutation routes return fragments, settings use unified `GET/POST /settings`, `POST /messages` dispatches leading slash commands or accepts a user message, `PUT /chats/{chat}/messages/{message}` edits a user message and truncates later history, `POST /messages/complete` starts background completion, `POST /messages/retry` prepares a failed completion retry, `GET /messages/tools` streams tool-call and terminal HTML over SSE, `GET /sw.js` serves the service worker for root scope, and `GET /static/` serves embedded assets.
- `templ/*.templ` contains source components despite using package name `templates`. Edit these source files, then regenerate. `static/` assets are versioned through `staticAssetVersion` in `templ/layout.templ`; bump it whenever embedded static assets change.
- `themes/` embeds five built-in Omarchy `colors.toml` palettes (`rose-pine` (Rose Pine Light), `rose-pine-dark`, `nord`, `tokyo-night`, `og` (OG)) parsed and validated at startup with a standard-library flat-TOML parser. Only the fixed IDs resolve, so unknown slugs are rejected and there is no path-based lookup. Each theme carries ID, label, mode, raw palette, and an inline CSS custom-property style including `color-scheme`. The selected slug persists in typed `settings.theme` (DB constraint rejects other values; empty update leaves it unchanged, NULL renders Rose Pine Light). Full pages set `data-theme`, the variable style, and `theme-color` on `<html>`; after a settings fragment swap, `static/app.js` copies `data-theme-*` attributes from the swapped `#settings-page` onto the live document. CSS `:root` fallback variables mirror the Rose Pine Light default.
- `static/` is embedded into the executable. Restart `go run .` after asset changes. htmx and `hx-sse` 4.0.0 are vendored there; `hx-sse.js` catches rejected reader cancellation during fetch-body cleanup. Completion SSE sends unnamed `<hx-partial>` updates, while `static/app.js` contains persistent presentation behavior, completion network-error recovery, theme application, and successful-save cleanup for preserved secret inputs. Settings include current picker values so out-of-band refreshes preserve unsaved chat selections. PWA support is `static/manifest.json`, generated PNG icons, and `static/sw.js` (registered from `app.js`, served at root scope with a fetch listener only; no caching). There is no npm build pipeline.
- `db/schema.sql` defines typed settings, including ntfy endpoint/topic and backend-only API key storage, theme slug, per-model endpoint protocol preferences, and ordered remote MCP server definitions with backend-only bearer tokens. It also defines `chats`, position-ordered `messages` with nullable undo groups, and normalized ordered tables for tools, prompt append definitions/selections/snapshots, user-image BLOBs, tool calls, and Responses provider output. Only opaque protocol values (tool arguments and individual Responses output payloads) remain JSON text. `openDatabase` uses one rollback-journal connection with foreign keys and a busy timeout.
- `db.InsertMessage` atomically persists a base row and its ordered children; chats are created through `db.AllocateChat` or updated through `db.UpsertChat`, which atomically replaces each chat's tool and append selections. `db.ReplaceUserMessage` keeps the edited row's ID and position while atomically deleting later history. `db.UndoLatestTurn` hides the latest active user turn in a durable LIFO group, while `db.RedoLatestTurn` restores the newest group; accepted replacement branches delete hidden groups. `db.GetMessageSnapshot` loads one transactional active-history snapshot and hashes base and child rows; `db.AppendCompletion` obtains a writer lock, rejects changed history, chooses the next stored position, and atomically appends generated messages. `db.AllocateChat` creates a chat preloaded with default-enabled tools and appends. Built-in prompt append text is embedded from `db/default_appends/*.md`; configured definitions and selected IDs are relational rows expanded only when completion history is sent to the model. Existing DBs get versioned migrations in `migrateDatabase` on startup.
- `llm.Client` is non-streaming and constructor-configured. Its endpoint argument must be a full Responses, Messages, or Chat Completions URL. Recognized suffixes enable exact-HTTP-500 fallback across sibling `/responses`, `/chat/messages`, and `/chat/completions` paths; successful protocol choices are stored per model and tried first later. User images are sent as protocol-specific inline base64 content. Model discovery reports image input as supported, unsupported, or unknown from provider metadata; unknown models are allowed and validated by completion. The server reads `LLM_KEY`, `LLM_MODEL`, `LLM_ENDPOINT`, and `SEARXNG_URL` directly and does not load a `.env` file.
- `commands.Registry` validates and dispatches slash commands before message persistence. Commands run only when `/` is the first input byte, receive an unsplit argument string, and return htmx headers or templ fragments without entering model history. Built-ins are `/new`, `/undo`, `/redo`, `/history`, `/settings`, and `/rename <title>`.
- `llm.NewConversation` creates a stateful, non-concurrent conversation around a client and optional `tools.Registry`. Initial messages may be supplied to the constructor; `Send` appends a user message, while `Complete` resumes from existing history.
- Conversations validate complete assistant responses before mutating history or executing tools. Valid function calls are executed through the registry, appended as `tool` messages with matching `tool_call_id` values, and sent back to the model. Consecutive tool-call chains are limited per conversation via `SetMaxToolRounds`, defaulting to 16 rounds; the limit is configurable in settings (1-100).
- Message text is limited to 1 MiB after prompt appends. Multipart message submissions accept up to four PNG, JPEG, or WebP images, with 5 MiB per image and 16 MiB total raw image data. Settings forms are limited to 1 MiB, ntfy settings to 16 KiB, and completion, retry, and rename forms to 16 KiB. Chat titles use the first non-empty line capped at 120 runes. Completion resumes a stored snapshot, rejects stale persistence with a retryable conflict, and is limited to one active task per chat in each process. Tasks outlive initiating browser requests, publish final fragments over 30-second-heartbeat SSE, and retain terminal state for five minutes so reconnecting pages can replay it; successful persisted responses schedule best-effort metadata-only ntfy notifications with a five-second timeout; interrupted user-ended history renders retry UI after process restart.
- `ntfy/` contains a standard-library publisher that validates HTTP(S) endpoints and topic names, sends bearer authentication without redirects, and never includes remote response bodies in errors.
- Chat-history links use scoped `hx-boost` navigation: full `GET /?chat=N` responses remain deep-linkable while htmx selects and swaps only `main`; htmx 4 refetches history and keeps no client history cache for chat privacy.
- `tools.Registry` validates definitions and invocation objects. `CapabilityTool` groups multiple model functions under one selectable capability, and `Registry.With` derives a registry with request-scoped tools. The `git` capability exposes compact `git_tree`, `git_read`, `git_search`, `git_log`, and `git_diff` functions backed by one request-scoped, read-only public HTTPS clone session. `tools/mcp` connects selected remote Streamable HTTP servers per completion, discovers namespaced tools, applies optional bearer authentication without redirects, and closes every session after completion; it does not support stdio. Each `Tool.Execute` implementation must still validate arguments against its own schema before side effects.
