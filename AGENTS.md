# Purpose

- Build the LLM chat UI as server-rendered hypermedia. Return templ-rendered HTML fragments for interactions; do not turn it into a client-rendered JSON application.
- Browser-side dependencies are limited to htmx, a-h/templ, and basic CSS. Do not add a JavaScript or CSS framework. Prefer readable modern CSS, including nesting where useful.

# Workflow

- Go is pinned to 1.25.3 in `go.mod`.
- A fresh checkout has no generated template Go files. Run `go run github.com/a-h/templ/cmd/templ@v0.3.1020 generate` before building, and after every `templ/*.templ` change. `templ/*_templ.go` is ignored; never edit it manually.
- Run the app with `go run .`; it listens on fixed address `:8080`. Accounts are created through the normal `/signup` form; no account bootstrap environment variables or setup page are required.
- `KRITUI_ENCRYPTION_KEY` is mandatory: standard base64 of exactly 32 random bytes, read directly from the environment and validated before the database opens. Generate it with `openssl rand -base64 32`; never commit a real key, generate one silently, or load `.env` in the app.
- Only edit files specified by the user. If you need to edit other files, ask before doing so.
- Full verification: `go test ./...` then `go vet ./...`. PDF page-image tests require Poppler's `pdfinfo` and `pdftoppm`; the remaining tests use local `httptest` servers.
- Browser verification: this repository has no local Playwright test suite. Whenever the user asks to test via Playwright, use the Playwright MCP tools against a running `go run .` instance; never add or run a repository-local Playwright package.
- `Dockerfile` generates templates, runs full tests and vet, then builds the binary. Keep every imported package directory in its explicit `COPY` list. Build and runtime stages both require Git because Git-tool tests and production Git tools execute its CLI. Both stages also install Poppler because PDF page-image conversion uses `pdfinfo` and `pdftoppm`.
- `.forgejo/workflows/container.yml` publishes commit-SHA and `main` tags to the Forgejo registry after successful `main` builds. Registry credentials remain organization Actions settings, never repository files.
- Focus a package with `go test ./internal/app`, `go test ./llm`, `go test ./tools`, or `go test ./tools/git`; focus one test with, for example, `go test ./llm -run '^TestComplete$'`.
- After large changes, update the AGENTS.md file accordingly. Keep it concise.

# Architecture

- `main.go` is the entrypoint. It embeds the browser assets in `static/` and `db/schema.sql`, then hands them to `app.Run`. `internal/app/server.go` is the HTTP implementation. `newMux` registers `GET/HEAD /healthz`, `/sw.js`, `/logo.png`, `/favicon.ico`, and the `/static/` prefix as public assets, plus `GET/HEAD/POST /login` and `/signup`; `POST /logout` remains session-protected. Go 1.25 `net/http.NewCrossOriginProtection` wraps the entire mux, including auth routes, while `auth.middleware` protects every other route. Protected `GET /` renders the page, history and chat mutation routes return fragments, settings use unified `GET/POST /settings`, `POST /messages` dispatches leading slash commands or accepts a user message, `PUT /chats/{chat}/messages/{message}` edits a user message and truncates later history, `GET/HEAD /chats/{chat}/messages/{message}/attachments/{position}` serves an owned active-message PDF inline with Range support and no-store, `POST /messages/complete` starts background completion, `POST /messages/retry` prepares a failed completion retry, and `GET /messages/tools` streams tool-call and terminal HTML over SSE.
- `internal/app/auth.go`, `internal/app/auth_handlers.go`, and `internal/app/password.go` implement username/password auth, sessions, and password hashing; user and session queries live in `db/`. Signup is open, with no email, verification, or reset flows. New accounts receive built-in defaults, never another account's custom settings or secrets. Usernames are case-insensitive, 3-32 characters, starting with an ASCII letter, digit, or underscore and then allowing letters, digits, underscore, dot, or hyphen. Passwords require at least 12 Unicode code points and at most 1024 UTF-8 bytes and use salted PBKDF2-HMAC-SHA256 with 600000 iterations. Sessions store only the token SHA256 hash; the host-only cookie is `Path=/`, `HttpOnly`, `SameSite=Lax`, persistent for 30 days, and Secure by default through `KRITUI_SECURE_COOKIES` (actual TLS always sets Secure). Multiple sessions are allowed, and logout revokes only the current session.
- Fresh databases seed an unclaimed, disabled Skrittle account in row `1` with an empty password hash; signing up with the case-insensitive username Skrittle sets its first password, enables the account, and claims legacy data on the same ID. Existing databases keep chats, settings, keys, images, tools, and other data attached to user ID `1`, and schema version 25 names that previously blank account Skrittle. Skrittle has no admin role or extra privileges; other usernames create ordinary accounts with built-in defaults. After Skrittle is initialized, signup cannot reset its password. Auth and private HTML responses are no-store, while static asset cache headers are unchanged.
- `templ/*.templ` contains source components despite using package name `templates`. Edit these source files, then regenerate. `static/` assets are versioned through `staticAssetVersion` in `templ/layout.templ`; bump it whenever embedded static assets change.
- `themes/` embeds six built-in `colors.toml` palettes: `rose-pine`, `rose-pine-dark`, `nord`, `forest-night`, `matte-black`, and `1975`. The Matte Black default matches the Kritui (copy) Paper palette, while 1975 is a light brutalist theme based on usgraphics.com (white page, black hairline borders, dark-green `#00794c` accent, gold `#ffb700`, signal-red `#e7040f`). A standard-library flat-TOML parser validates palettes at startup; only fixed IDs resolve. Each theme carries its ID, label, mode, raw palette, and inline CSS variables including `color-scheme`. The selected slug persists in typed per-account `settings.theme`; empty updates preserve it, and NULL renders Matte Black. Schema version 19 renames `omarchy` to `matte-black` and `og` to `rose-pine-dark` (replacing the previous Rose Pine Dark palette) while preserving existing settings; schema version 20 adds `1975` to the accepted set, and schema version 21 removes `tokyo-night` (remapping stored values to `matte-black`). Full pages set `data-theme`, variable styles, and `theme-color` on `<html>`; settings swaps copy `data-theme-*` attributes onto the live document. CSS fallback variables mirror Matte Black.
- The UI uses a 960px shell, square controls, a bottom Settings/Options/History bar, and bundled Inter/JetBrains Mono fonts in `static/fonts/`. The shell is headerless: native `.shell-scroll` contains the chat viewport, and `.shell-viewport` with the composer fills the available height. Chat, Settings, and History keep their scrollbars inside the panel. Downward routing yields to controls, the composer, and nested scroll areas. A passive sizing listener fits the panel and composer directly to the outer offset without transitions or animation. Mobile and portrait layouts drop outer side gutters and honor safe-area insets while preserving inner content padding. `GET /chats/{chat}/summary` returns escaped title and visible-message count HTML; history responses refresh counts out of band. Preserve the composer, picker, panel, message, and SSE DOM contracts when changing layout. `internal/app/ui_test.go` covers summary behavior and theme migration/persistence.
- `static/` is embedded into the executable. Restart `go run .` after asset changes. htmx and `hx-sse` 4.0.0 are vendored there; `hx-sse.js` catches rejected reader cancellation during fetch-body cleanup. Completion SSE sends unnamed `<hx-partial>` updates, while `static/app.js` contains persistent presentation behavior, completion network-error recovery, theme application, and successful-save cleanup for preserved secret inputs. Settings include current picker values so out-of-band refreshes preserve unsaved chat selections. PWA support is `static/manifest.json`, generated PNG icons, and `static/sw.js` (registered from `app.js`, served at root scope with a fetch listener only; no caching). PWA assets remain public before login, manifest identity, start URL, and scope stay `/`, login and signup share manifest and mobile metadata, and installed sessions survive relaunch. There is no npm build pipeline.
- `db/schema.sql` defines typed settings, including ntfy endpoint/topic and backend-only API key storage, user LLM key+endpoint with backend-only key storage, an optional encrypted per-account system prompt base and compaction prompt, theme slug, per-model endpoint protocol preferences, and ordered remote MCP server definitions with backend-only bearer tokens. It also defines `chats`, position-ordered `messages` with nullable undo groups, and normalized ordered tables for tools, prompt append definitions/selections/snapshots, user-attachment BLOBs, tool calls, and Responses provider output. `llm.Message.Attachments` holds ordered `llm.UserAttachment` values; images and PDFs share the legacy `message_user_images` table, with zero dimensions for PDFs and no schema migration. Only opaque protocol values (tool arguments and individual Responses output payloads) remain JSON text. `openDatabase` uses one rollback-journal connection with foreign keys, `secure_delete`, `temp_store=MEMORY`, and a busy timeout. Schema version 22 adds backend-only user LLM key+endpoint; version 23 adds tool-result elision mode, user-turn count, token budget, and summarization model, defaulting to `none`; version 24 adds `users` and `sessions` and per-user ownership, with `settings.id` becoming the user ID rather than a singleton; version 25 names the legacy blank username exactly Skrittle without changing account IDs or data ownership.
- Database content is encrypted at rest with standard-library AES-256-GCM using the mandatory `KRITUI_ENCRYPTION_KEY`. Encrypt chat titles, message text for every role, tool arguments and results, provider output, prompt append definitions and snapshots, attachment bytes and filenames, pending and receipted inbox text and attachments, stored per-account system and compaction prompts, LLM key and endpoint, ntfy key, endpoint, and topic, and MCP token and URL. Leave IDs, ownership, usernames, password and session hashes, timestamps, model and tool names, and attachment types and dimensions plaintext. Startup migrates existing values atomically into encrypted envelopes; text values use the `enc:v1:` prefix, and byte fields use a binary envelope. Each value uses a fresh 12-byte nonce, and authenticated data binds field, owner, and stable row ID; reject a wrong key before mutations. `secure_delete` plus `VACUUM` removes logically freed plaintext pages, but physical erasure on SSDs, copy-on-write filesystems, backups, or snapshots is not guaranteed. Use the same key across restarts and deployments; there is no rotation. AES-GCM detects payload tampering, not whole-database rollback or metadata tampering. Public shares keep their separate client-side crypto. Production validates the key, calls `db.RequireStorageEncryption` as a one-way process-wide guard, and injects the cipher with `db.WithStorageCipher` into request and worker contexts; `context.WithoutCancel` preserves it for background work, and the startup migration passes the cipher explicitly. After the guard, a missing cipher context errors instead of reading or writing plaintext; pre-guard plaintext compatibility exists only for trusted direct tests, never production. Schema version 31 marks the storage-format boundary so older version-30 binaries refuse a database that may now contain encrypted values instead of writing new plaintext. Schema version 33 adds the nullable encrypted `settings.system_prompt`; NULL or whitespace means the built-in `llm.DefaultSystemPrompt()`. Schema version 34 adds the nullable encrypted `settings.compaction_prompt`; NULL, whitespace, or the built-in default means `llm.DefaultCompactionPrompt()`.
- `db.InsertMessage` atomically persists a base row and its ordered children; chats are created through `db.AllocateChat` or updated through `db.UpsertChat`, which atomically replaces each chat's tool and append selections. `db.ReplaceUserMessage` keeps the edited row's ID and position while atomically deleting later history. `db.UndoLatestTurn` hides the latest active user turn in a durable LIFO group, while `db.RedoLatestTurn` restores the newest group; accepted replacement branches delete hidden groups. `db.GetMessageSnapshot` loads one transactional active-history snapshot and hashes base and child rows; `db.AppendCompletion` obtains a writer lock, rejects changed history, chooses the next stored position, and atomically appends generated messages. `db.AllocateChat` creates a chat preloaded with default-enabled tools and appends. Built-in prompt append text is embedded from `db/default_appends/*.md`; configured definitions and selected IDs are relational rows expanded only when completion history is sent to the model. Existing DBs get versioned migrations in `migrateDatabase` on startup. `db.WithUser(ctx, userID)` scopes per-user queries; an absent context defaults to the legacy Skrittle account `1` only for trusted direct callers and tests, while auth middleware always installs the signed-in account.
- `llm.Client` is non-streaming and constructor-configured. Its endpoint argument must be a full Responses, Messages, or Chat Completions URL. Recognized suffixes enable fallback on HTTP 500 or an explicit structured unsupported-protocol HTTP 400 across sibling `/responses`, `/chat/messages`, and `/chat/completions` paths; successful protocol choices are stored per model and tried first later. Messages requests try the alternate `/messages` or `/chat/messages` spelling only after HTTP 404 or 405 and remember the working URL within the client. Protocol selection uses provider responses rather than provider or model-name rules, preserving the configured origin and query. User images are sent as protocol-specific inline base64 content; PDFs use Responses `input_file`, Messages `document`, or Chat Completions `file` parts. PDF filenames are preserved as `filename` or the Messages document `title`. Model discovery reports image and PDF input as supported, unsupported, or unknown from provider metadata, including top-level `modalities.input`. When PDFs are unsupported but images are supported, the app renders up to 200 pages with Poppler `pdfinfo`/`pdftoppm` into JPEG attachments named `<pdf name> - page N.jpg`, capped at 80 MiB, and snapshots the hidden automatic `pdf-images` append into the user message. That append is visible in the message's Appends control but omitted from Settings and the chat append picker. A model that supports neither PDFs nor images rejects the message. Stored LLM endpoint/key and model protocol preferences come from SQLite per account; environment key/endpoint remain deployment-wide overrides/fallback, winning field by field, and both populated hide model-connection controls; `LLM_MODEL` also remains deployment-wide. The server reads `LLM_KEY`, `LLM_MODEL`, `LLM_ENDPOINT`, and `SEARXNG_URL` directly and does not load a `.env` file.
- Each account may customize its system prompt base and tool-result compaction prompt in Settings. `llm.DefaultSystemPrompt()` returns the built-in editable base; `llm.PromptContext.SystemPrompt` replaces it, while invariant PDF-citation instructions plus current time, client timezone, and PDF links are always appended. `db.GetSystemPrompt` returns the effective base and `db.SaveSettings` stores NULL for blank, whitespace, or built-in-default text so future default updates apply. `llm.DefaultCompactionPrompt()` returns the built-in instruction for summarizing older tool results; `Conversation.SetToolResultSummaryPrompt` replaces it only in the separate tool-free summary request and invalidates cached summaries when it changes. `db.GetCompactionPrompt` mirrors the system prompt resolution, and both values are limited to 64 KiB and preserved byte-for-byte. Settings posts may omit either field to preserve it; submitted text is validated before the atomic save and rerendered verbatim on unrelated validation errors, including when the other prompt is invalid. Title generation keeps its dedicated prompt.
- `commands.Registry` validates and dispatches slash commands before message persistence. Commands run only when `/` is the first input byte, receive an unsplit argument string, and return htmx headers or templ fragments without entering model history. Built-ins are `/new`, `/undo`, `/redo`, `/history`, `/settings`, and `/rename <title>`.
- `llm.NewConversation` creates a stateful, non-concurrent conversation around a client and optional `tools.Registry`. Initial messages may be supplied to the constructor; `Send` appends a user message, while `Complete` resumes from existing history.
- Optional per-account chat-title generation stores its toggle and model in schema version 28. The initial message fragment starts independent `POST /chats/{chat}/title` work alongside completion. `llm.Client.CompleteText` sends only the dedicated title system prompt and first user-message text, without tools or chat session identity. Title work has a 20-second timeout, preserves concurrent manual renames, survives initiating request cancellation, and returns a History HTML refresh independently of completion SSE; chat replies never wait for it.
- Completed assistant responses use an owner-only share dialog to choose a built-in theme, whole chat or recent prompt/response, editable title, and Markdown. Recent shares include the nearest preceding active user text and edited assistant Markdown; whole-chat shares include active user/assistant text only, excluding tools and attachments. `POST /chats/{chat}/messages/{message}/share` prepares a transient HTML snapshot; `/share/publish` stores only versioned AES-256-GCM ciphertext with a 12-byte nonce. Schema version 30 retires legacy plaintext shares without changing chat history. Inline sender JavaScript generates each key locally; the copied URL carries it only in `#key=...`, never in HTTP requests or SQLite. Public `GET/HEAD /s/{token}` uses a SHA256-hashed random token and returns a deterministic ciphertext bootstrap with a hash-authorized inline decryptor, no external assets. Decrypted HTML renders in an opaque, script-disabled sandbox with sanitized Markdown and the theme frozen at creation. Snapshots survive source deletion. The icon-only control supports repeated copying and clears successful-copy feedback after four seconds. Header and footer Kritui links point to `https://kritui.skrittle.net`.
- Prompt steering and FIFO queueing use a durable, account-scoped SQLite inbox. Composer Send becomes Steer during completion; Queue waits for the complete response/tool chain. Pending prompts retain submission IDs, model/tool selections, prompt-append snapshots, and attachments across reloads/restarts; users can remove inputs, change delivery mode, and retry parked work. Pending rows sit above the bottom control bar, with delivery badges and no heading, counter, or Resume button. Schema version 26 adds normalized inbox/receipt and completion-state tables; version 27 adds per-chat pin state. History orders pinned chats before unpinned chats, then by recency, using a pin-aware keyset cursor; pin changes do not modify chat timestamps. `internal/app/inbox_handlers.go` coordinates admission and one server-owned worker per chat; no provider/tool calls run while its short boundary lock is held. `llm.Conversation.SetRoundBoundary` checkpoints complete assistant/tool batches, delivers steering input before the next provider call, and can continue after a final response when steering arrived. `db.CheckpointCompletion` preserves digest conflict checks and atomically assigns message IDs, promotes pending input, and records whether continuation remains. Queued turns start without browser participation; failures park remaining work for retry. SSE refreshes `#message-history` and `#prompt-inbox` through templ-rendered partials while preserving the composer. `templates.ActiveCompletionView` keeps trailing tool batches in the expanded live list across checkpoints and reloads; steering messages and final responses archive preceding tool groups.
- Completion system prompts list canonical URLs for PDFs in active user-message history. PDF citations use Markdown links with `#page=N`, where N is the 1-based physical PDF page index. Assistant Markdown links to same-origin attachment URLs open the existing PDF dialog with the fragment preserved in both the iframe and Open in new tab link; modified clicks retain native link behavior. `templates.MessageAttachmentURL` supplies the shared card and prompt URL format.
- Conversations validate complete assistant responses before mutating history or executing tools. Valid function calls are executed through the registry, appended as `tool` messages with matching `tool_call_id` values, and sent back to the model. Consecutive tool-call chains are limited per conversation via `SetMaxToolRounds`, defaulting to 16 rounds; the limit is configurable in settings (1-100).
- `llm.Conversation.SetToolResultElision` shapes outbound context before each provider round without changing stored message content, tool-call IDs, or Responses metadata. Per-account Chat Defaults offer `none`, `current_turn`, `last_user_turns` (1-1000, including the current turn), `tool_result_budget` (1-10000000 estimated tokens, oldest consumed results first), and `summarize` (earlier turns, using a selected model with the effective connection and its own protocol preference). Token estimates use UTF-8 byte length divided by four, rounded up; fresh trailing tool batches and marker costs can exceed the budget. Summaries are cached within one conversation, retain original text when longer, and propagate provider failures. Settings reveal and enable only the selected mode's parameter controls.
- Tool-result elision reports actual per-request reductions before the next provider call. Schema version 32 persists display-only `message_tool_calls.result_elided` metadata, excluded from provider payloads and conversation snapshot digests. SSE updates both archived and live tool names: elided results use muted text, or muted red for errors. Errored request arguments and their brackets stay muted red regardless of elision. Full results sent again clear the flag; original results and error text remain intact.
- Message text is limited to 1 MiB after prompt appends. Multipart message submissions accept up to four mixed PNG, JPEG, WebP, or PDF attachments, with 20 MiB per file and 80 MiB total raw data. PDF detection uses the file signature; PDFs render as filename cards, and sent cards open a full-screen native viewer through the authenticated range-capable attachment endpoint, with an Open in new tab fallback, while composer cards remain static previews. The endpoint scopes attachments to the owning signed-in account, matching chat, message, and index, and returns 404 for foreign, hidden, or missing attachments. Attachment-only messages are allowed. Preserve the legacy `image` multipart field and attachment DOM IDs. Settings forms are limited to 1 MiB, ntfy settings to 16 KiB, and completion, retry, and rename forms to 16 KiB. Chat titles use the first non-empty line capped at 120 runes. Completion resumes a stored snapshot, rejects stale persistence with a retryable conflict, and is limited to one active task per chat in each process. Background completion and ntfy contexts retain the owning account, and tracker entries, SSE reconnects, and private tool results are scoped per user. Tasks outlive initiating browser requests, publish final fragments over 30-second-heartbeat SSE, and retain terminal state for five minutes so reconnecting pages can replay it; successful persisted responses schedule best-effort metadata-only ntfy notifications with a five-second timeout; interrupted user-ended history renders retry UI after process restart.
- `ntfy/` contains a standard-library publisher that validates HTTP(S) endpoints and topic names, sends bearer authentication without redirects, and never includes remote response bodies in errors.
- Chat-history links use scoped `hx-boost` navigation: full `GET /?chat=N` responses remain deep-linkable while htmx selects and swaps only `main`; htmx 4 refetches history and keeps no client history cache for chat privacy.
- `tools.Registry` validates definitions and invocation objects. `CapabilityTool` groups multiple model functions under one selectable capability, and `Registry.With` derives a registry with request-scoped tools. The `git` capability exposes compact `git_tree`, `git_read`, `git_search`, `git_log`, and `git_diff` functions backed by one request-scoped, read-only public HTTPS clone session. `tools/mcp` connects selected remote Streamable HTTP servers per completion, discovers namespaced tools, applies optional bearer authentication without redirects, and closes every session after completion; it does not support stdio. Each `Tool.Execute` implementation must still validate arguments against its own schema before side effects.
